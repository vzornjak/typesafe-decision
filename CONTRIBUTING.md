# Contributing

Thanks for looking at this project. It is a small, deliberately conservative
codebase: an **advisory** decision layer where local deterministic code stays
authoritative and the model is only a sensor. Contributions are welcome as long
as they keep that property.

## Ground rules

0. **Read and follow [`archi.ai`](archi.ai).** It is the canonical architecture,
   roadmap, phase-gate policy, and Definition of Done. Do not create a competing
   roadmap or silently skip a gate. A durable change to architecture, scope,
   sequencing, or safety policy must update `archi.ai` in the same PR and explain
   the evidence and migration/rollback impact.
1. **No new runtime dependencies.** The scripts are Python standard library
   only, on purpose — they have to run inside constrained agent sandboxes
   (iSH/Alpine on iOS, minimal containers). A PR that adds a third-party import
   to `scripts/` will be rejected.
2. **No network in tests, ever.** The suite sets `TYPESAFE_OFFLINE=1` and
   monkeypatches `socket.create_connection` to raise. If your test needs an API
   response, add a `StubTransport`/`ReplayTransport` case in
   `scripts/replay_harness.py`.
3. **No real data in the repository.** No production logs, no real corpora, no
   real API transcripts, no personal data, no session identifiers, no keys.
   Fixtures must be generated by `tests/generate_fixtures.py`.
4. **No absolute host paths as dependencies.** The only `/var/minis/...` string
   allowed is the documented, overridable default log path, and only in files
   that also document `TYPESAFE_DEFAULT_LOG`. `tests/run_tests.py` enforces
   this.
5. **No claim of official affiliation.** This project is unofficial and must
   keep saying so. Do not add wording implying endorsement, partnership or
   support by TypeSafe AI.
6. **Advisory stays advisory.** Do not add code paths where a model answer
   grants authorization, bypasses a deterministic safety check, or upgrades a
   fail-closed outcome to a confident one.

## Before you open a PR

```bash
python3 tests/run_tests.py --verbose
```

All six stages must pass: `py_compile`, `selftest` (25), `regressions` (119),
`fixture_integrity`, `secret_scan`, `absolute_path_scan`. CI runs exactly this.

## Adding a regression test

Every behaviour change needs a test. Tests live in `scripts/tests_phase1.py` and
are registered with the `@test("<FINDING>", "<description>")` decorator.

```python
@test("P1-7", "a short, specific sentence describing the guaranteed behaviour")
def _my_test():
    t = rh.StubTransport(answer_fn=rh.rank_answer_fn(fit={"a": 0.9}))
    out = rank_via(t, {"query": "q", "candidates": [{"id": "a"}, {"id": "b"}]})
    assert out["decision"] == "winner", out
```

Notes:

- A duplicated `(finding, name)` pair is a **hard failure**, not a warning. The
  summary reports `tests` and `unique_tests` separately precisely so nobody can
  inflate the count. Pick a genuinely new description.
- Use `@final_gate(...)` only for checks that must observe the complete
  side-effect surface of the whole suite (e.g. "no secret-looking value appears
  in any log this suite produced").
- Use the `TMP` directory for any file the test writes. Never write outside it.
- Never reference a path outside the repository or `TMP`.

## Changing or regenerating fixtures

Fixtures are frozen and hash-pinned. If a legitimate change requires new
fixtures:

1. Edit `tests/generate_fixtures.py` — never hand-edit files in
   `tests/fixtures/`.
2. Run `python3 tests/generate_fixtures.py` to regenerate the data *and* the
   manifest.
3. Run the full suite and commit both the fixtures and the manifest.
4. Explain in the PR why the fixture change was necessary. A fixture change
   that makes a previously failing assertion pass needs a very good reason.

Fixture data must remain synthetic: generated prose, authored scores,
`.test`/`.example` hostnames, no personal data. `provenance.txt` must keep
saying `origin=synthetic`, and a test asserts it.

## Evidence and claims

This project has been burned by a contaminated evaluation once already (see
[`docs/RETRACTION-shortlist-v1.1.md`](docs/RETRACTION-shortlist-v1.1.md)). So:

- Distinguish **measurement**, **calibration** and **projection** explicitly.
- Never cite a number produced by a run where the evaluation requirements were
  the gold checklist.
- Always state the parameters used, and flag any deviation from documented
  defaults.
- If you add a quality claim, add the dataset, protocol and code to reproduce
  it — or label it clearly as a projection.

Synthetic-fixture tests lock *relative policy properties*. They are not, and
must never be presented as, quality evaluations.

## Commit and PR style

- Small, focused commits. One behavioural change per PR where possible.
- Imperative subject line, ≤72 characters.
- The PR body should say: what changed, why, which tests cover it, and whether
  any documented behaviour, default or claim changed.
- Behaviour changes must update `CHANGELOG.md`, and documented contract changes
  must update `SKILL.md` and `README.md` in the same PR.

## Versioning

The version lives in `scripts/ts_common.py` (`__version__`) and is asserted by
tests. The log schema version (`SCHEMA_VERSION`) is separate and only bumps when
the audit-row shape changes — a schema bump requires `report.py` to keep reading
older rows.

## Security issues

Do **not** open a public issue for a vulnerability. See
